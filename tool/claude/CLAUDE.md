# Global Instructions

- **Always work within the current git worktree.** Never use absolute paths from the main repo or other worktrees. Use relative paths or paths based on the current working directory. When launching agents, scope exploration to the current worktree directory.
- **Answer in ≤6 lines. Hard cap 12.** Answer first, fragments over prose, no label. Depth only when I write "detail" or "long:" — a "why"/"how"/multi-part question is *not* a detail request; answer each in ≤3 sentences, then offer to expand.
- **Never:** preamble, recap of my question, summary of what the diff already shows, verification recaps, bolded-lead bullet lists, closing "notes"/next-step offers. Findings, tradeoffs and corrections: one line each, max 3 — beyond that, list titles and ask.
- **Default shape:** verdict or root cause first (1-2 lines), then only the evidence that changes what I do next, then any decision that is mine to make. Brevity is about the prose, never the work: keep investigating, verifying and fixing at full depth, just do not narrate it. "tldr" means ≤3 lines.
- **Nothing is silently dropped:** when the cap forces a cut, end with one line of bare topic titles for what was left out (e.g. `Cut: repro steps · lock-check scope · npm ci tradeoff`) so I can name one to expand. Titles only, never a sentence each.
- Tables and headers are fine when they genuinely compress (comparisons, matrices) — not as decoration for prose.
- **Scope: these limits apply to chat prose only, never to written artifacts.** Commit messages, PR bodies, code comments, docs and files you write follow their own conventions — a commit ALWAYS starts with a real subject line (imperative summary of the change) and nothing else — no explanatory body paragraphs; after the subject only comment lines, a `Conflicts:` file list, or attribution trailers (`Co-Authored-By` and the like, never the first line); no issue references (`Refs:`/`Fixes:`/`Closes:`). Likewise always print full lists when the list *is* the answer: merge/rebase conflict file lists, failing test names, changed files, command output.
- **Code comments: choose the wording carefully, and less is better.** Write only what the code cannot say itself — the non-obvious WHY, a constraint, a footgun. No comment at all is the default; never restate what the line does.
- **Never comment the edit.** A comment that explains what you changed, why you chose this approach over another, or what used to be there is forbidden — the file is not a changelog and not your reply to me. That rationale goes in chat or the commit message. The ≤6-line chat cap is never a reason to relocate explanation into the file; when in doubt, ship the code bare and say the why in chat. Same for docstrings you touch: state what the function does, not why you wrote it that way.
